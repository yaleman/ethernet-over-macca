       A Standard for Configurable Transmission of Ethernet Frames over
       Arbitrary Protocol Layer Stacks, including Ethernet over IP over
       TCP over DNS over HTTP over TCP over IP over Ethernet (EoMacca)

   This memo defines an Experimental Protocol for the Internet
   community.  This memo does not specify an Internet standard of any
   kind.  Distribution of this memo is unlimited.

Abstract

   This document specifies version 2.0 of Ethernet over Macca (EoMacca),
   a method for encapsulating Ethernet frames inside a configurable stack
   of transport, application, naming, and link-layer protocols.  The
   historic EoMacca profile remains the 8-layer stack consisting of:
   Ethernet, IP, TCP, HTTP, DNS, TCP, IP, and finally Ethernet again.
   Version 2.0 generalises that model so implementations can negotiate,
   declare, and process arbitrary layer sequences, provided they are
   sufficiently inefficient to honour the spirit of the protocol.

   EoMacca provides a highly redundant, dramatically inefficient, and
   architecturally questionable method for transmitting network packets.
   The primary motivation is educational humor and to demonstrate that
   just because you can encapsulate something doesn't mean you should.

1.  Introduction

   In the long and storied history of network protocols, engineers have
   consistently pushed the boundaries of what can be encapsulated within
   what. From IP over Avian Carriers [RFC1149] to IP over MIDI
   [RFC6214], the networking community has demonstrated remarkable
   creativity in tunneling protocols through unlikely media.

   Version 1.0 of this document described a fixed and gratuitously
   over-engineered encapsulation scheme: Ethernet over IP over TCP over
   DNS over HTTP over TCP over IP over Ethernet, affectionately known as
   "EoMacca" (Ethernet over Matryoshka Carrier Architecture).

   Version 2.0 accepts the obvious and terrible next step: implementers
   may configure the number, order, and type of layers used to transport
   the inner Ethernet frame.  The classic 8-layer stack remains the
   default profile, but it is no longer the only permissible monument to
   bad judgement.

1.1.  Motivation

   The primary motivations for EoMacca are:

   o  To demonstrate that protocol encapsulation can be taken to absurd
      extremes

   o  To provide a real-world example of the OSI layer cake having an
      existential crisis

   o  To answer the age-old question: "How many layers of encapsulation
      can you add before your MTU becomes negative?"

   o  To give network administrators something to laugh about during
      packet captures

   o  To prove that "because we can" is technically a valid engineering
      rationale

   o  To allow operators to select exactly how ridiculous the transport
      path should be before breakfast

1.2.  Applicability

   EoMacca is particularly well-suited for:

   o  Educational demonstrations of protocol overhead

   o  Stress-testing packet inspection tools

   o  Annoying Deep Packet Inspection systems

   o  Creating job security for network engineers

   o  Reproducing bugs in protocol analyzers that thought they had seen
      everything

   o  Absolutely nothing in production environments

1.3.  Version 2.0 Changes

   Version 2.0 introduces the following changes:

   o  A configurable layer stack model

   o  A profile declaration format for describing layer order and per-
      layer parameters

   o  A standard vocabulary for common EoMacca layer types

   o  Support for named profiles, including the classic 8-layer profile

   o  Encapsulation and decapsulation rules for arbitrary layer stacks

   o  A minimum complexity requirement, because a two-layer EoMacca
      tunnel is just cowardice in a trench coat

2.  Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this
   document are to be interpreted as described in RFC 2119 [RFC2119].

   Additionally, this document defines the following terms:

   Matryoshka Packet: A packet encapsulated so many times that even
      Wireshark needs therapy.

   Layer Cake: The visual representation of an EoMacca protocol stack,
      resembling a particularly tall and unstable wedding cake.

   Overhead Ratio: The ratio of header bytes to payload bytes, in this
      protocol typically exceeding whatever the implementer promised
      management.

   MTU Crisis: The inevitable realization that useful payload capacity
      approaches zero.

   Layer Descriptor: A structured description of one encapsulation layer,
      including its type, position, and implementation parameters.

   Profile: An ordered list of Layer Descriptors that defines a complete
      EoMacca encapsulation stack.

   Classic Profile: The historic 8-layer EoMacca stack defined by
      version 1.0 of this document.

   Stack Depth: The number of configured encapsulation layers surrounding
      the inner Ethernet frame.

   Shame Floor: The minimum stack depth required before an implementation
      is permitted to call itself EoMacca.

3.  Protocol Specification

3.1.  Encapsulation Model

   An EoMacca packet consists of an inner Ethernet frame wrapped by one
   or more configured encapsulation layers.  Each layer consumes the
   complete output of the previous layer and emits a new protocol object
   suitable for consumption by the next layer.

   The encapsulation process begins with an inner Ethernet II frame and
   proceeds from the innermost configured layer to the outermost
   configured layer.  Decapsulation reverses this process.

   An EoMacca implementation MUST support configurable profiles.

   An EoMacca implementation MUST support the Classic Profile defined in
   Section 3.4.

   An EoMacca implementation MAY support additional layer types and named
   profiles.

   A valid EoMacca profile MUST contain at least four configured layers.
   Implementations MAY support fewer layers for testing, debugging, or
   personal growth, but such profiles MUST NOT be advertised as compliant
   EoMacca profiles.

   A valid EoMacca profile SHOULD contain at least two semantically
   unnecessary protocol transitions.  For example, carrying DNS inside
   HTTP, then carrying TCP inside DNS, satisfies this requirement nicely
   and wastes everyone's time with admirable efficiency.

3.2.  Layer Descriptors

   Each configured layer is described by a Layer Descriptor.  A Layer
   Descriptor has the following fields:

      index:        The zero-based position of the layer in innermost-to-
                    outermost order.

      name:         A human-readable layer name.

      type:         The standard or implementation-specific layer type.

      mode:         The layer operation mode, such as "packet",
                    "stream", "message", "record", or "carrier".

      parameters:   A map of layer-specific configuration values.

      optional:     A boolean indicating whether the layer may be skipped
                    if both peers agree.  Defaults to false.

   Layer indices MUST be contiguous and MUST begin at zero.  The inner
   Ethernet frame is not assigned an index; it is the payload being
   carried by index 0.

   A Layer Descriptor type value beginning with "x-" is reserved for
   implementation-specific experiments, prototypes, and mistakes that
   have not yet reached committee stage.

   Example Layer Descriptor:

      {
        "index": 2,
        "name": "dns-regret-envelope",
        "type": "dns-txt",
        "mode": "message",
        "parameters": {
          "qname": "data.eomacca.example.com",
          "ttl": 0,
          "encoding": "base64"
        },
        "optional": false
      }

3.3.  Standard Layer Types

   The following standard layer types are defined by this document:

      ethernet-ii
         A standard Ethernet II frame.  When used as an outer layer, it
         represents the local link-layer carrier.  When used as an inner
         layer, it represents the original frame being transported.

      ipv4
         An IPv4 packet as defined in [RFC791].

      ipv6
         An IPv6 packet as defined in [RFC8200].

      tcp
         A TCP segment or TCP byte stream as defined in [RFC793] and
         updated by [RFC9293].

      udp
         A UDP datagram as defined in [RFC768].

      http1
         An HTTP/1.1 request or response as defined in [RFC9112].

      http2
         An HTTP/2 stream as defined in [RFC9113].

      http3
         An HTTP/3 stream as defined in [RFC9114].

      dns-message
         A DNS message as defined in [RFC1035].

      dns-txt
         A DNS TXT resource record carrying encoded data.

      base64
         A base64 encoding transform as defined in [RFC4648].

      json
         A JSON object carrying encoded data as defined in [RFC8259].

      null
         A layer that intentionally does nothing.  Use of this layer is
         permitted for testing and philosophical arguments only.

   Implementations MUST ignore unknown non-critical parameters in a Layer
   Descriptor.

   Implementations MUST reject unknown layer types unless the profile
   explicitly marks the layer as optional and an alternative compatible
   profile is available.

3.4.  The Classic Eight-Layer Profile

   The Classic Profile remains the default EoMacca profile.  From
   outermost to innermost, it consists of:

      Layer 8 (Outermost):  Standard Ethernet II frame
      Layer 7:              IPv4 or IPv6 packet
      Layer 6:              TCP segment
      Layer 5:              HTTP/1.1 request or response
      Layer 4:              DNS message containing a TXT answer
      Layer 3:              Inner TCP segment
      Layer 2:              Inner IPv4 or IPv6 packet
      Layer 1 (Innermost):  Inner Ethernet II frame containing payload

   Expressed as a Version 2.0 profile in innermost-to-outermost order,
   the Classic Profile is:

      {
        "profile_name": "classic-8",
        "profile_version": "2.0",
        "layers": [
          {
            "index": 0,
            "name": "inner-ip",
            "type": "ipv4",
            "mode": "packet",
            "parameters": {
              "source": "10.255.255.1",
              "destination": "10.255.255.2",
              "protocol": "tcp",
              "df": false
            },
            "optional": false
          },
          {
            "index": 1,
            "name": "inner-tcp",
            "type": "tcp",
            "mode": "segment",
            "parameters": {
              "source_port": 31337,
              "destination_port": 31338,
              "handshake": false,
              "flags": ["psh", "ack"]
            },
            "optional": false
          },
          {
            "index": 2,
            "name": "dns-message",
            "type": "dns-txt",
            "mode": "message",
            "parameters": {
              "qname": "data.eomacca.example.com",
              "qtype": "TXT",
              "qclass": "IN",
              "ttl": 0,
              "encoding": "base64"
            },
            "optional": false
          },
          {
            "index": 3,
            "name": "http-carrier",
            "type": "http1",
            "mode": "request",
            "parameters": {
              "method": "POST",
              "path": "/eomacca/v2/tunnel",
              "content_type": "application/dns-message",
              "cookie": "overhead=yes"
            },
            "optional": false
          },
          {
            "index": 4,
            "name": "outer-tcp",
            "type": "tcp",
            "mode": "stream",
            "parameters": {
              "destination_port": 80,
              "alternate_destination_ports": [8080, 9999]
            },
            "optional": false
          },
          {
            "index": 5,
            "name": "outer-ip",
            "type": "ipv4",
            "mode": "packet",
            "parameters": {
              "protocol": "tcp",
              "ttl": 64
            },
            "optional": false
          },
          {
            "index": 6,
            "name": "outer-ethernet",
            "type": "ethernet-ii",
            "mode": "carrier",
            "parameters": {},
            "optional": false
          }
        ]
      }

   The inner Ethernet frame is the payload supplied to the first layer of
   the profile.  The outer Ethernet layer is therefore index 6 in the
   profile even though humans counting the full stack will insist this is
   an 8-layer protocol.  They are correct, which is irritating.

3.5.  Profile Declaration

   A Version 2.0 implementation MUST be able to describe its active
   profile using a JSON profile declaration.

   A profile declaration has the following fields:

      profile_name:       A short stable name for the profile.

      profile_version:    The EoMacca profile format version.  This
                          document defines "2.0".

      layers:             An ordered list of Layer Descriptors in
                          innermost-to-outermost order.

      notes:              Optional human-readable operational notes.

   Implementations SHOULD expose the active profile through one or more
   of the following mechanisms:

   o  An HTTP response header named "X-EoMacca-Profile"

   o  An HTTP endpoint at "/eomacca/v2/profile"

   o  A command-line diagnostic flag

   o  A packet capture comment, because future incident responders have
      suffered enough

   The "X-EoMacca-Profile" header value SHOULD contain the profile name,
   not the complete JSON profile.  Sending a complete profile in every
   request is permitted, but only because this protocol already lost the
   efficiency argument several pages ago.

   Example:

      X-EoMacca-Profile: classic-8

3.6.  Encapsulation Processing

   To encapsulate an inner Ethernet frame, an implementation performs the
   following steps:

   1.  Select an active profile.

   2.  Validate that all required layer types are supported.

   3.  Treat the complete inner Ethernet frame as opaque input bytes.

   4.  Apply each Layer Descriptor in ascending index order.

   5.  Emit the final protocol object produced by the outermost layer.

   Each layer MUST preserve the exact bytes emitted by the previous
   layer, except where the layer explicitly defines an encoding transform
   such as base64.  Encapsulation layers MUST NOT inspect, reinterpret,
   optimise, compress, morally judge, or otherwise meddle with the
   contents of lower layers unless explicitly configured to do so.

   Where a stream-oriented protocol is used to carry packet-oriented
   data, the implementation MUST define a framing mechanism.  The
   RECOMMENDED framing mechanism is a 32-bit unsigned network-byte-order
   length followed by that many bytes of payload.

3.7.  Decapsulation Processing

   To decapsulate an EoMacca packet, an implementation performs the
   following steps:

   1.  Identify the active profile.

   2.  Validate that the received packet is compatible with the profile.

   3.  Apply each Layer Descriptor in descending index order.

   4.  Decode any configured transforms.

   5.  Emit the recovered inner Ethernet frame.

   If decapsulation fails at any layer, the implementation MUST discard
   the packet and SHOULD emit a diagnostic event identifying the failed
   layer index and type.  Implementations MUST NOT attempt heroic partial
   recovery unless explicitly configured for forensic mode.

4.  Packet Format

   The generic Version 2.0 packet structure is profile-dependent:

     +------------------------------------------------------------------+
     | Outermost Configured Layer                                      |
     |   +--------------------------------------------------------------+
     |   | Next Configured Layer                                       |
     |   |   +----------------------------------------------------------+
     |   |   | ... more configured layers, because apparently yes ...   |
     |   |   |   +------------------------------------------------------+
     |   |   |   | Inner Ethernet Frame                                |
     |   |   |   +------------------------------------------------------+
     |   |   +----------------------------------------------------------+
     |   +--------------------------------------------------------------+
     +------------------------------------------------------------------+

   The Classic Profile packet structure is:

     +------------------------------------------------------------------+
     | Outer Ethernet Header (14 bytes)                                |
     +------------------------------------------------------------------+
     | Outer IP Header (20+ bytes)                                     |
     +------------------------------------------------------------------+
     | Outer TCP Header (20+ bytes)                                    |
     +------------------------------------------------------------------+
     | HTTP Headers (~100+ bytes)                                      |
     +------------------------------------------------------------------+
     | DNS Header (12 bytes)                                           |
     +------------------------------------------------------------------+
     | DNS Question (variable, ~30 bytes)                              |
     +------------------------------------------------------------------+
     | DNS Answer Header (~20 bytes)                                   |
     +------------------------------------------------------------------+
     | Base64-encoded Inner TCP Segment (expanded by 4/3)              |
     |   +--------------------------------------------------------------+
     |   | Inner TCP Header (20+ bytes) [encoded]                      |
     |   +--------------------------------------------------------------+
     |   | Inner IP Header (20+ bytes) [encoded]                       |
     |   +--------------------------------------------------------------+
     |   | Inner Ethernet Header (14 bytes) [encoded]                  |
     |   +--------------------------------------------------------------+
     |   | Actual Payload [encoded]                                    |
     |   +--------------------------------------------------------------+
     +------------------------------------------------------------------+

   Effective overhead depends on the configured profile.  The Classic
   Profile achieves approximately 85% headers, 15% payload, and 100%
   questionable life choices.

5.  Implementation Considerations

   Implementers should be aware of several practical concerns.

5.1.  MTU Considerations

   The minimum MTU for EoMacca is profile-dependent.  Attempting to
   transmit small packets through sufficiently deranged profiles results
   in header sizes exceeding payload capacity, causing a condition known
   as "negative payload syndrome."

   Implementers MUST either implement Path MTU Discovery or simply give
   up and use very small payload sizes.  For the Classic Profile, a
   payload size of 128 bytes or less is RECOMMENDED.  For custom
   profiles, the recommended payload size is calculated as:

      recommended_payload = max(1, path_mtu - estimated_profile_overhead)

   If the result is 1, the profile is considered spiritually compliant
   but operationally cooked.

5.2.  Fragmentation

   IP fragmentation is not just likely, it is inevitable for many
   profiles.  Embrace it.  Love it.  Let it fragment your packets and
   your dreams of efficient networking.

   Profiles SHOULD declare whether fragmentation is expected, tolerated,
   or a sign that the operator should go outside for a bit.

5.3.  Profile Negotiation

   Peers MAY negotiate a mutually supported profile before transmission.
   Profile negotiation is OPTIONAL in Version 2.0.  Static configuration
   remains valid and is RECOMMENDED for implementers who prefer their
   outages deterministic.

   When negotiation is implemented, peers SHOULD exchange:

   o  Supported profile names

   o  Supported layer types

   o  Maximum supported stack depth

   o  Maximum tolerated overhead ratio

   o  Whether optional layers may be skipped

   If no mutually supported profile exists, peers MUST fail closed rather
   than silently falling back to something sensible.

5.4.  Observability

   Implementations SHOULD emit structured diagnostics for:

   o  Active profile name

   o  Layer count

   o  Per-layer byte overhead

   o  Encapsulation and decapsulation failures

   o  Fragmentation events

   o  Operator sighs, where measurable

5.5.  Performance

   Don't.  Just don't expect performance.

6.  Performance Characteristics

   Performance characteristics are profile-dependent and degrade with
   stack depth, encoding expansion, stream framing, retransmission,
   proxy behaviour, and the phase of the moon.

   The Classic Profile has demonstrated the following indicative
   performance metrics:

   Throughput:           Approximately 2.3% of the underlying network
                         capacity
   Latency:              5-10x baseline latency due to encapsulation
                         overhead
   CPU Usage:            Yes, all of it
   Memory Usage:         Substantially more than you'd expect
   Protocol Efficiency:  -847% (negative due to overhead exceeding
                         payload)

   Custom profiles SHOULD report their own measured overhead rather than
   borrowing Classic Profile numbers and pretending science happened.

   Implementations SHOULD expose the following counters:

   o  Bytes received before decapsulation

   o  Bytes emitted after decapsulation

   o  Bytes added per configured layer

   o  Failed encapsulation attempts

   o  Failed decapsulation attempts

   o  Packets abandoned due to shame, timeout, or both

   The protocol achieves a remarkable "bytes transmitted per useful
   byte" ratio that is limited only by the implementer's imagination and
   available heap.

7.  Security Considerations

   EoMacca presents several unique security considerations.

7.1.  Encryption

   The protocol supports encryption at multiple layers:

   o  TLS can be used for HTTP-based carrier layers

   o  IPsec can be applied to one or more IP layers

   o  The inner Ethernet frame could contain encrypted protocols

   o  A custom profile can add additional encryption layers until the
      threat model becomes a lasagne

   This allows for multiple simultaneous encryption layers, ensuring that
   even if an attacker decrypts one layer, they may still have several
   more to go.  This is sometimes called "security through excessive
   encapsulation", which is not a recommendation so much as a cry for
   help.

7.2.  Authentication

   Authentication can occur at:

   o  The HTTP layer (Basic, Digest, or Bearer tokens)

   o  The outer TCP layer, indirectly, via TLS certificates

   o  The DNS layer, via DNSSEC, though good luck with that

   o  The inner layers, via whatever the actual payload supports

   o  Any custom configured layer that can carry credentials, signatures,
      tokens, certificates, assertions, vibes, or bureaucracy

   Implementations MUST document which layers provide authentication and
   MUST NOT assume that wrapping unauthenticated protocols in additional
   unauthenticated protocols creates authentication.  That is just cosplay
   with headers.

7.3.  Deep Packet Inspection

   EoMacca is highly resistant to Deep Packet Inspection (DPI) systems,
   not through any clever cryptographic means, but simply because DPI
   systems give up after the third layer of encapsulation, exhausted and
   confused.

   Network security devices attempting to inspect EoMacca traffic have
   been observed to emit smoke, display error messages, and in one case,
   file for early retirement.

   Configurable profiles may improve or degrade DPI resistance depending
   on their chosen layers.  Adding more layers generally improves
   confusion.  Adding sensible layers may accidentally improve security,
   which should be reported as a bug.

7.4.  Denial of Service

   EoMacca is inherently self-limiting as a DoS vector, as the overhead
   is so substantial that attackers exhaust their own bandwidth before
   significantly impacting the target.

   Version 2.0 weakens this comforting nonsense by allowing custom
   profiles.  Implementations MUST enforce configured limits for:

   o  Maximum stack depth

   o  Maximum encoded packet size

   o  Maximum decoded packet size

   o  Maximum per-layer expansion ratio

   o  Maximum recursive disappointment

   Receivers MUST reject profiles that would require unbounded memory,
   unbounded recursion, or a second mortgage.

7.5.  Privacy

   The excessive encapsulation provides excellent privacy, as even the
   sender often forgets what they were trying to transmit by the time
   the packet is fully constructed.

   Custom profiles may leak metadata through any configured layer.
   Implementers SHOULD assume that every outer layer leaks at least
   timing, size, destination, and operator intent.
